# Dialogue & choice script functionality: a survey of prior art

## 1. Purpose and scope

Ticket 14 (`docs/issues/14-dialogue-scripts-read-write-flags.md`) is the first slice where a Script does more than emit a static line: it reads a Flag to branch, and a Dialogue choice writes a Flag back. That slice is scoped tightly (one flat per-Student Flag store, `.say()` only, one flag set per choice). Before deciding what comes *after* ticket 14, this note asks a narrower question than "how should dialogue work here": what does the *feature surface* of dialogue/choice scripting look like in systems that solo/small-team narrative-heavy games actually ship with — Undertale, visual novels, JRPGs — so that gaps between "what ticket 14 builds" and "what that feature surface contains" can be named, prioritized, and (separately, later) run through this repo's own `/grill-with-docs` → `/to-spec` → `/to-tickets` pipeline. This note does not propose designs, does not touch ADR-0009 (TypeScript builder, not a parsed DSL) or ADR-0011 (no pause channel) as settled, and does not write tickets.

## 2. Feature catalogue

Primary sources consulted: **Ink** (inkle, `WritingWithInk.md`), **Yarn Spinner** (`docs.yarnspinner.dev`), **Ren'Py** (`renpy.org/doc/html`), and **RPG Maker MZ** event commands (`rpgmakerofficial.com`, the official MZ help manual). Undertale is included only where the point is that no official source exists — see the note at the end of the table and in Sources.

| # | Capability | How each primary source implements it |
|---|---|---|
| 1 | **Branching on state/flags** | **Ink**: a weave choice can be gated by a boolean/numeric test in curly braces, e.g. `* { not visit_paris } [Go to Paris] -> visit_paris`. **Yarn Spinner**: `<<if $reputation > 10>>` around lines, or as a trailing condition on an option. **Ren'Py**: a `menu` choice takes a Python `if` clause, e.g. `"Fly above." if drank_tea:`. **RPG Maker MZ**: the `Conditional Branch` command tests a Switch, Variable, Self Switch, and more, wrapping subsequent commands. |
| 2 | **Choice-level visibility: shown-but-disabled vs. fully hidden** | **Ren'Py** is the one source with an explicit, documented distinction: a failed `if` on a menu choice hides it by default, but `config.menu_include_disabled = True` renders it as a disabled/greyed-out button instead. **Yarn Spinner**: a failed `<<if>>` on an option makes it "unavailable"; the docs explicitly leave *how* to render that (hidden vs. disabled) up to the game's dialogue-view implementation — it is not itself opinionated. **Ink**: a failed conditional choice is simply absent from the generated choice list — no built-in "visible but disabled" state; a story would have to fake it by always showing the choice text and having its target knot immediately explain why it failed. **RPG Maker MZ**: `Show Choices` has no native per-choice condition at all — the documented technique is to leave a choice's text blank ("Choices left blank will not be displayed"), driven by a `Control Variables`/`Conditional Branch` command beforehand — hidden-only, no disabled state. |
| 3 | **One-time vs. repeatable choices/lines** | **Ink** has this as first-class, default syntax: `*` choices vanish after being chosen once; `+` ("sticky") choices persist and can be re-chosen. **Ren'Py**: the `menu` statement's `set` clause (e.g. `set menuset`) automatically removes a choice's caption from future presentations of that same `menu` label once picked — an explicit one-time-choice mechanism. **RPG Maker MZ**: no built-in one-time-choice primitive; the documented idiom for a one-time *event* (not choice) is a second Event Page gated on a Self Switch (see #9). **Yarn Spinner**: no built-in once-only/sticky option state in the fetched docs — the pattern is manual, via a variable set with `<<set>>` and checked with `<<if>>`. |
| 4 | **Setting multiple flags/variables per choice** | All four support arbitrary logic under a choice branch, not just one assignment: **Ink** allows multiple `~` logic lines under a `*`/`+` choice; **Yarn Spinner** allows multiple `<<set>>` commands under an option; **Ren'Py** allows arbitrary Python statements in a menu choice's indented block; **RPG Maker MZ** allows any number of `Control Switch`/`Control Variables` (and other) commands nested under a `Show Choices` branch. |
| 5 | **Arithmetic on variables (not just booleans)** | **Ink**: full expression syntax incl. `+ - * / %` and functions like `POW()`, `RANDOM(a,b)` on numeric `VAR`s. **Yarn Spinner**: numeric variables support `+ - * / %` and comparison operators (`eq`, `gt`, `lt`, …); a variable's type (bool/number/string) is fixed at `<<declare>>` and never changes. **Ren'Py**: variables are plain Python, so arbitrary arithmetic/expressions apply. **RPG Maker MZ**: `Control Variables` has explicit Set/Add/Sub/Mul/Div/Mod operations, operands from a constant, another variable, a random range (`-99999999..99999999`), game data, or a JavaScript "Script" escape hatch. |
| 6 | **Speaker/character identity per line** | **Yarn Spinner**: a line prefixed `Name:` (no space before the colon) is parsed into a distinct character field passed to the game alongside the text. **Ren'Py**: `Character()` objects (`define e = Character("Eileen", who_color="#c8ffc8")`) are bound to a short local variable and prefixed onto say-statements (`e "Hello, world."`); styling (name color, text color, window skin) is configurable per character. **RPG Maker MZ**: `Show Text` has a dedicated Name field plus a Face Graphic picker, both editable per message. **Ink**: no built-in speaker concept — pure text engine; speaker attribution is left to the host, conventionally via hashtag line tags (`# speaker: Bob`). |
| 7 | **Sequencing multiple speakers in one exchange** | All are "just write consecutive lines with a different speaker attribution each time": **Yarn Spinner** consecutive `Name: text` lines; **Ren'Py** consecutive say-statements with different `Character()` variables; **RPG Maker MZ** consecutive `Show Text` commands each with its own Name field; **Ink** consecutive lines each carrying a different speaker tag by convention (no engine-level concept of "current speaker"). |
| 8 | **Conditional text substitution (variable interpolation in a line)** | **Ink**: `{friendly_name}` interpolates a string variable directly into prose, and `{x > 0: Positive|Negative}` interpolates conditionally on an expression — the same curly-brace mechanism as conditional choices. **Yarn Spinner**: `{$variableName}` interpolates a variable's value into line text. **RPG Maker MZ**: message "control characters" substitute in-line, e.g. `\N[n]` (actor name), `\V[n]` (variable value). **Ren'Py**: not directly confirmed from the pages fetched for this note (Ren'Py's dialogue text uses Python-string-adjacent substitution conventions) — flagged as *unconfirmed from primary source here*, not asserted. |
| 9 | **Re-entrant nodes (different content on a revisit — directly ticket-14-shaped)** | **Ink** has this as a first-class, automatic feature: every knot/stitch carries a "read count" usable as a number in a conditional (`{seen_clue > 3} ...`), plus `TURNS_SINCE(-> knot)` for "how long ago." No manual flag needed for the simple case. **RPG Maker MZ**'s documented idiom is **Self Switches**: an event can have multiple numbered Pages, each with its own display condition (including a Self Switch A–D); only the highest-ID page whose conditions match is shown, so "Page 1 = first-visit dialogue, Page 2 = gated on Self Switch A being ON = post-visit dialogue" is the *standard*, named pattern for exactly "NPC says something different after you've talked to them once." **Yarn Spinner** has a dedicated mechanism too, not just a manual one: *line groups*/*node groups* plus its Saliency system pick which of several candidate lines/nodes to run next by strategy — the built-in "Best Least Recently Viewed" strategy is explicitly a revisit-aware selector (sorts eligible content by how many times it's already been shown, preferring the least-seen), alongside the plainer manual route of a `<<set>>` variable checked with `<<if>>`. **Ren'Py**: `renpy.seen_label()` (referenced in official docs, not deep-read here) and/or persistent/store variables checked in an `if`. |
| 10 | **Nested/tree-shaped branching vs. flat choice-then-continue** | **Ink**'s "weave" is explicitly tree-shaped: nested choice levels (`*`, `**`, `***`) with matching nested gather levels (`-`, `--`, `---`) that recombine branches without a new knot per branch. **Yarn Spinner** supports nesting indented options inside other options within one node body (a compact local tree), as an alternative to jumping to a whole new node per branch. **Ren'Py**: branching deeper than one `menu` block is done by jumping each choice to its own `label`, which can itself contain another `menu` — a tree built out of jumps, not a single-block weave syntax. **RPG Maker MZ**: `Show Choices` branches are literally nested blocks of event commands; deeper branching means nesting another `Show Choices` inside a branch — imperative nesting, no dedicated tree syntax. |
| 11 | **"Goto"/jump between named sections** | **Ink**: diverts, `-> knot_name` / `-> knot_name.stitch_name`. **Yarn Spinner**: `<<jump NodeName>>`. **Ren'Py**: `jump label_name` (one-way; per the docs, "there's no way to return to where you've jumped from"). **RPG Maker MZ**: its Flow Control command set includes `Label` ("creates a jump location") and `Jump to Label` ("transfers execution to a named label within the same event page") — a direct, official within-event goto, not just cross-event reuse via Common Events (#12). |
| 12 | **Calling one script/section from another (with return)** | **Ink**: tunnels — `-> knot ->` calls into a knot and `->->` returns to just after the call site; tunnels can chain (`-> a -> b -> done`). **Ren'Py**: `call label` pushes a return address; the called label's `return` statement resumes execution right after the `call`. **RPG Maker MZ**'s Flow Control page documents a `Common Events` command that "invokes a separate common event and resumes the current sequence after it finishes" — a call/return model at the event-command level. **Yarn Spinner**: `<<detour NodeTitle>>` is exactly this — it "will return to the node that called it afterwards" (via an explicit `<<return>>` or the node simply ending), distinct from the one-way `<<jump>>`; one documented edge case: if the detoured-into node itself uses `<<jump>>`, "the return stack is cleared" and the original caller is never returned to. |
| 13 | **Random/weighted line variation** | **Ink** has this as dedicated, named syntax under "Alternatives": *sequences* (`{a|b|c}`, shows the next each time, sticks on the last), *cycles* (`{&a|b|c}`, loops), *once-only* (`{!a|b|c}`, shows nothing once exhausted), and *shuffles* (`{~Heads|Tails}`, randomized) — four distinct, composable variation strategies in one syntax family. **Yarn Spinner** also has a dedicated mechanism, via *line groups* and its Saliency system: several candidate lines are declared as a group, and a saliency strategy picks which one plays — "Best" scores candidates by complexity/specificity of their conditions, "Best Least Recently Viewed" explicitly biases toward content shown least often (a built-in weighted/anti-repeat selector, not a bare `random()` call). **RPG Maker MZ**: `Control Variables`' "Random" operand (range `-99999999..99999999`) can drive variable-line-selection logic, but there is no dedicated "vary this line" primitive — it's assembled from Conditional Branch + Control Variables. **Ren'Py**: nothing dedicated found in the docs checked here (Python's `random` module is reachable directly, but that's general-purpose, not a documented dialogue-authoring feature). |
| 14 | **Timed or auto-advancing choices** | Not documented as a first-class feature in *any* of the four primary sources checked. Yarn Spinner's `<<wait N>>` pauses dialogue playback for N seconds but is a delay before continuing, not a countdown attached to a choice. This looks like a genuine common gap — where it exists in shipped games it is typically bespoke UI/game code layered on top of the scripting system, not something the scripting layer itself models. |
| 15 | **Choice-triggered side effects beyond flags (sound, items, quest state, etc.)** | **Ink**: `EXTERNAL` function declarations let a knot/choice call out to host-game code as a side effect. **Yarn Spinner**: custom `<<commands>>` are explicitly the documented mechanism for this — the docs give "playing audio files, changing character sprites or portraits, modifying visual effects, updating game state" as the canonical use cases. **Ren'Py**: arbitrary Ren'Py/Python statements (play sound, `$ inventory.add(...)`, jump, etc.) sit directly in a menu choice's block — no special syntax needed. **RPG Maker MZ**: any event command (Change Items, Change Party Member, Play SE, …) can be placed inside a `Show Choices` branch — this is central to how the whole event system is used, not an edge case. |
| 16 | **Localization / string-table separation** | **Yarn Spinner** has the most explicit, tooled version: lines get an auto-generated `#line:xxxx` id tag, and a Yarn Project can export/import a CSV strings table keyed by that id for translators, who touch only the language/text columns. **Ren'Py** has a first-class `translate` statement / translation-file workflow built into the engine (per official docs; not deep-read for this note). **Ink** and **RPG Maker MZ**: no built-in localization/string-table tooling was found in the sources checked here — third-party/community tooling fills the gap for RPG Maker specifically. |
| 17 | **Save/resume mid-dialogue** | **Ren'Py** and **RPG Maker MZ** both bake this in at the engine level — the save system is core, and current dialogue/event position is part of what a save captures; not an opt-in dialogue feature. **Ink**'s runtime API is explicit and documented in `RunningYourInk.md`: `story.state.ToJson()` serializes "the complete runtime state of your story, including all variables and progression data," and `story.state.LoadJson(savedJson)` restores it — a first-class save/resume API, separate from the authoring doc (`WritingWithInk.md`) this note otherwise draws from. **Yarn Spinner**: not confirmed from the pages checked for this note — flagged as a gap in this survey, not a claimed absence. |
| 18 | **Portrait/expression changes** | **Ren'Py** has the richest documented primitive: a `Character()` bound to an image tag lets a say-statement carry expression attributes between the name and the text, with `@` separating a permanent change from a temporary one for that line only (`e happy @ vhappy "Really!"`). **RPG Maker MZ**: `Show Text`'s Face Graphic field is set per message. **Yarn Spinner**: achieved via custom commands (e.g. a hypothetical `<<portrait Sarah happy>>`), per the same "commands drive presentation" pattern as #15. **Ink**: no visual layer at all — text-only engine; portraits would be entirely host-side, likely driven by line tags. |
| 19 | **Voice/audio hooks** | **Ren'Py** has a dedicated `voice` statement tied to the say-statement (`voice "line0001.ogg"` before a line; `voice sustain` to carry playback across an interaction), plus per-character voice-mute tagging. **RPG Maker MZ**: `Play SE`/`Play ME` commands can be sequenced alongside `Show Text`, but are not bound to a specific line the way Ren'Py's `voice` is. **Yarn Spinner**: via custom commands, same pattern as #15/#18. **Ink**: no built-in audio hook; would go through `EXTERNAL` functions or tags. |

**On Undertale specifically**: the brief asked this be investigated for the "flag/counter-driven permanent dialogue change," "different line on repeat visits," and "route flag" angles. There is **no official public documentation of Undertale's scripting or dialogue-authoring system** — Toby Fox has not published a script format, engine internals, or an authoring API. What's community-documented (e.g. the Undertale Wiki's "Genocide Route" page, or the *Undertale Yellow* wiki's "Technical:Flags" page) comes from data-mining game files and community reverse-engineering, not developer-confirmed sources, and Undertale is built directly in GameMaker (imperative code + a bespoke, non-public text-scripting mini-language for battle/overworld text), not a reusable dialogue-scripting product with a documented authoring surface the way Ink/Yarn/Ren'Py/RPG Maker are. This note therefore does **not** cite Undertale as a source for any row in the table above, per the instruction to flag this source-quality gap explicitly rather than inventing citations. The *shape* of what Undertale is known (informally) to do — a permanent global flag that survives a reset and permanently alters future dialogue, NPC lines that change after N visits — is fully covered by row 9 (re-entrant nodes) and row 3 (one-time state) above using sources that do have public documentation.

## 3. Mapped against this repo's current state

For each row, where does it sit relative to `apps/web/src/scripts/script.ts` (`createScript().say(...).build()`), the ticket-14 scope, and `docs/spec/spec.md`'s existing Out of Scope list?

| # | Capability | Status here |
|---|---|---|
| 1 | Branching on flags | **Covered by ticket 14 as written** — "A Script can branch its Dialogue based on a Flag already being set" is an explicit checklist item; `CampFire.ts` already shows the shape (`ctx.flags.talked_to_campfire`). |
| 2 | Shown-but-disabled vs. hidden choices | **Near-term extension.** Ticket 14 only requires a choice to exist or not; a `.choice(text, { visible: cond })` vs. `.choice(text, { enabled: cond })` distinction on the builder is a small, additive extension of the same shape once `.choice()` itself lands. No architectural blocker — this is a builder-API and overlay-rendering decision, not an ADR-level one. |
| 3 | One-time vs. repeatable choices | **Near-term extension**, expressible today with Flags (a choice's availability = a flag check) — no new architecture needed, just builder ergonomics (Ink's `*`/`+` shorthand is a nicety, not a requirement). |
| 4 | Multiple flags/variables set per choice | **Plausible near-term extension** of `.choice()`'s eventual shape — ticket 14's own checklist item 2 says "each naming *a* Flag" (singular); generalizing to "a set of Flag writes" is additive, not architectural. |
| 5 | Arithmetic on variables | **Requires a decision this repo hasn't made.** `docs/spec/spec.md`'s Flag definition is explicitly "boolean/number/string values only — no nested structures, no quest/inventory modeling," and Flags already *can* hold numbers — but nothing today does arithmetic on them (increment a counter, compare thresholds) versus simple set/overwrite (`setFlags` in `apps/web/src/state/flags.ts` is `Object.assign`, i.e. last-write-wins, not read-modify-write). Whether "Flags can be incremented/compared with `>`/`<` from a Script" is in-bounds for the existing flat Flag model, or is scope creep toward the explicitly-deferred "quest/variable modeling," is a real open question. |
| 6 | Speaker identity per line | **Explicitly out of scope right now** in spirit — not named in spec.md, but the whole system so far is one Entity → one implicit voice; no per-line speaker field exists in `Dialogue { lines: string[] }`. Plausible near-term extension (a line becomes `{ speaker?: string, text: string }`) with no architectural blocker. |
| 7 | Multiple speakers in one exchange | Same as #6 — falls out of #6 once a per-line speaker field exists; not currently modeled since `Dialogue` is just `string[]`. |
| 8 | Variable interpolation in a line | **Plausible near-term extension** — since Scripts are plain TypeScript (ADR-0009), template literals already give this for free (`` `Hello, ${ctx.flags.playerName}` ``) without any new builder feature. Likely the cheapest capability on this whole list to "add." |
| 9 | Re-entrant nodes (different line on revisit) | **This *is* ticket 14's last checklist item**, already scoped: "interact again, and confirm the Dialogue reflects the changed Flag." Ink's read-counts and RPG Maker's Self-Switch-gated pages are two working precedents for the *general* pattern (see row 9 above); this repo's chosen mechanism (a Script reading `ctx.flags` and branching with an `if`) is closest in spirit to RPG Maker's explicit-flag idiom, not Ink's automatic-read-count idiom — worth naming as a deliberate choice, not an oversight, if it comes up in grilling. |
| 10 | Nested/tree-shaped branching | **Plausible near-term extension of the builder shape**, bounded by ADR-0009: since ADR-0009 already chose "plain TypeScript, not a parsed DSL," a tree of choices leading to further choices is naturally expressible as nested function calls/callbacks in the fluent builder — no new architecture, just builder-API design work once `.choice()` exists (ticket 14 in flight now handles only flat "one round of choices"). |
| 11 | Goto/jump between named sections | **Not clearly needed yet** — a Script today is one function; "jump to another point in the same Script" is a plain `if`/`return` in TypeScript already. Only becomes a real question if Scripts get long enough to want the equivalent of Ink's knots/stitches inside one Script — no evidence of that need yet. |
| 12 | Calling one script from another | **Explicitly out of scope per spec.md, adjacent to it** — spec.md's Out of Scope calls out "entityId→script lookup table — only needed if one Script must serve multiple Entities; not built until that's a real case." Calling one Script module from another (import one TS module into another) is trivially possible today since Scripts are plain TS, but no builder-level "tunnel/call" primitive exists or has been asked for. |
| 13 | Random/weighted line variation | **Not currently possible for free** — could be authored manually in TypeScript (`Math.random()` inside a Script) without any builder change, since Scripts are plain code (ADR-0009's whole point). Not mentioned anywhere in spec.md; likely stays ad hoc rather than becoming a builder primitive unless a concrete authoring pain point shows up. |
| 14 | Timed/auto-advancing choices | **Requires an architectural decision this repo has explicitly declined to make**: any timed/auto-advance behavior that needs to *force* the Dialogue overlay or Player state on a clock brushes directly against ADR-0011's declined Host→Engine pause/resume channel, since "auto-advance after N seconds" implies the Host driving something the Player isn't controlling. Even a Host-only timer (no Engine involvement) is unaddressed by spec.md today. |
| 15 | Choice-triggered side effects beyond flags | **Partially covered / partially deferred.** Setting a Flag *is* a side effect and is ticket 14's core. Anything beyond Flags — "give item," "play sound," "start quest" — runs into spec.md's Out of Scope: "Full quest/variable/inventory modeling — Flags stay a flat key/value store." Playing a sound specifically isn't a Flag/quest concern and could plausibly be a Host-side effect a Script triggers directly (e.g. calling a Host audio function) without touching Flags at all — worth separating "needs quest modeling" from "needs a Script→Host side-effect channel" as two different asks. |
| 16 | Localization/string-table separation | **Not addressed anywhere in spec.md** — since Dialogue text is currently inline string literals inside TypeScript Scripts (`say('Howdy! am campfire!')`), there is no string-table layer at all yet. Not urgent for a solo/small-team playground, but worth flagging if the project ever needs non-English content or non-programmer copy edits — this is also the kind of requirement ADR-0009 itself names as the trigger for reconsidering the "TypeScript, not a parsed DSL" choice ("if non-programmer authoring becomes a real requirement"). |
| 17 | Save/resume mid-dialogue | **Already effectively covered by the current architecture, not by dialogue-specific work.** Because Dialogue v1 doesn't pause the Player (ADR-0011) and isn't itself a modal "story position" the way Ink/Ren'Py track one, there's no mid-dialogue state to resume — the overlay is transient per-Interaction, and the durable state is just the Flags it read/wrote, which ticket 11's store already persists. This only becomes a real question if Dialogue grows multi-step branching sequences that a Player could plausibly navigate away from mid-sequence. |
| 18 | Portrait/expression changes | **Requires new authoring assets/pipeline, not just a code change** — spec.md has no Entity portrait/expression concept, and `assets/` (gitignored, Tiled-sourced) has no obvious home for character-expression art yet. A plausible builder extension (`.say(text, { portrait: 'happy' })`) is easy; the asset pipeline behind it is a separate, unscoped question. |
| 19 | Voice/audio hooks | **Not addressed anywhere in spec.md.** Same shape as #15's "play sound" case — likely a Script→Host side-effect call, not a Flag concern, if it's ever wanted. |

## 4. Candidate follow-up research or grilling topics

Prioritized by how directly they bear on "what's the next ticket after 14," not in ticket form (tickets are `/to-tickets`' job, downstream of `/grill-with-docs` → `/to-spec`):

1. **`.choice()` builder shape** (rows 2, 3, 4, 10) — the single highest-leverage next grilling topic: ticket 14 is already adding the first `.choice()`; deciding its shape now (single flag vs. flag-set, visible-vs-enabled conditions, nested choices) avoids a second redesign right after ticket 14 lands. No ADR conflict — purely a builder-API/spec question.
2. **Per-line speaker + interpolation** (rows 6, 7, 8) — cheap (TypeScript template literals give interpolation for free; a speaker field is a small `Dialogue` shape change) and directly serves the "Undertale/visual-novel feel" the user described. No ADR conflict.
3. **Flag arithmetic vs. flat set/overwrite** (row 5) — needs grilling specifically because it sits on the boundary spec.md already drew ("no quest/variable modeling") — decide explicitly whether "increment a counter Flag" is in-bounds for the existing Flag model or is the first step toward the deferred quest/variable system. **No ADR conflict, but directly touches a boundary spec.md already committed to** — flag this tension explicitly when grilling rather than quietly widening Flags.
4. **Script→Host side effects beyond Flags** (rows 15, 19, and "play sound"/"give item" generally) — worth separating from quest/inventory modeling explicitly: a Script calling a Host function to play a sound doesn't obviously need quest/inventory modeling at all, and conflating the two in spec.md's existing Out of Scope may be over-broad. No ADR conflict.
5. **Portrait/expression pipeline** (row 18) — mostly an asset-authoring/guide question (`docs/guides/`), not an ADR-level one, but needs its own investigation into where such art would live given `assets/` is gitignored third-party content today.
6. **Timed/auto-advancing choices** (row 14) — **would require reopening ADR-0011** the moment "timed" means "the Dialogue overlay or Player state changes on a clock the Player doesn't control." A Host-only cosmetic timer (e.g. auto-selecting a choice after N seconds, with no Engine involvement) might *not* need it — worth grilling specifically to find the line between "needs the declined pause channel" and "doesn't."
7. **Save/resume mid-dialogue** (row 17) — low priority now (row 17's analysis: nothing to resume yet given non-blocking v1 Dialogue), but re-raise if Dialogue ever grows into multi-step branching sequences a Player could leave mid-way.
8. **Localization/string-table separation** (row 16) — lowest priority for a solo/small-team playground today, but the one item on this list that **directly matches the trigger ADR-0009 itself names** for reconsidering "TypeScript, not a parsed DSL" ("if non-programmer authoring becomes a real requirement"). Not a request to reopen ADR-0009 now — just the one item worth watching, since it's the exact condition the ADR names.
9. **Random/weighted line variation, calling one Script from another, goto/jump within a Script** (rows 13, 12, 11) — lowest priority; all three are already achievable in plain TypeScript today without any builder or architectural change (ADR-0009's whole premise), so there's no gap to close unless a concrete authoring pain point shows up first.
