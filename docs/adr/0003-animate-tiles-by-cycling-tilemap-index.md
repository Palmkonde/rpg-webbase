# Animate Tiled per-tile tiles by cycling their tilemap index, not via sprite overlays

Tiled authors per-tile animation metadata directly on image-collection tilesets (e.g. the campfire in `animationObject`: six frame images, each its own tile id, cycled via a `<animation>` list). The Engine's tilemap loading (`tiled-assets.ts`, `engine.ts`) only ever reads a tile's first-frame image and never reads or acts on that `animation` data, so any Tiled-authored animated tile currently renders as a permanently static single frame — not a bug in existing logic, just a capability that was never built.

We resolve it generically, not per-asset: any tile carrying Tiled's per-tile `animation` array is animated by cycling the existing `Phaser.Tilemaps.Tile`'s `.index` among the frame GIDs Tiled listed, on a timer honoring each frame's configured duration — extending the same per-tile pass already used to copy `tile.properties` onto tiles in `MapScene.create()`. We considered instead promoting animated tiles to standalone Phaser Sprites/GameObjects layered over the static tilemap (via Phaser's `AnimationManager`), which would double as a stepping stone toward interactive/Entity-like decorations later, but rejected it as speculative: nothing in this Engine's current scope calls for animated decoration to be interactive, and a sprite-overlay approach adds GameObject lifecycle/depth-sorting complexity the index-swap approach doesn't need. This keeps animated-tile rendering unconditional and Engine-owned — driven entirely by what Tiled authored, with no World Config involvement — consistent with how static tiles and collision (`ge_collide`) already work.
