# Script output generalizes to a discriminated union, not new ScriptBuilder methods or an imperative call

Making CG and Cutscene playable from a Script — not just game boot's hardcoded CG, and not just a bare `playCutscene(id)` primitive waiting for its own trigger path (issues #25-28) — needed a Script's return type to carry more than `Dialogue`. We considered a Script calling `playCG`/`playCutscene` imperatively as a side effect, and rejected it: Scripts are pure `ctx => output` functions (`adr/0009`), and a side channel into the Host's render state would break that. We considered growing `ScriptBuilder` with `.playCG(id)`/`.playCutscene(id)` terminal methods alongside `.say()`/`.choice()`, and rejected that too: the builder exists to accumulate Dialogue lines and choices, and a CG/Cutscene trigger has neither, so those methods would build nothing builder-shaped. Instead `Script`'s return type generalizes to a discriminated union — `Dialogue | CgTrigger | CutsceneTrigger`, each trigger just `{ type, id }` — and a Script produces a CG/Cutscene by returning that plain object directly, bypassing `ScriptBuilder` entirely for that case. The Host (`game-canvas.tsx`) switches on the returned `type` to call `setDialogue`, `playCG(id)`, or (once built) `playCutscene(id)`; whichever plays, the Player is frozen via the existing `setPaused` flag (`adr/0016`) for its duration, automatically and unconditionally rather than as something a Script author opts into.
