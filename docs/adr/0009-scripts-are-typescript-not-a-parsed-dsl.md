# Scripts are plain TypeScript via a builder API, not a parsed DSL

For what a Script looks like, we considered a data-only config (a YAML/JSON dialogue tree), a small parsed text DSL in the style of Ink or Yarn, and plain TypeScript authored through a small builder/fluent API (`say("...").choice("Yes", ...)`). We chose the TypeScript builder: it needs no parser, interpreter, or sandboxing to build and maintain, and gets full IDE/type-checking support for free. "A script system, like Unity, but simpler" was read as a simpler *authoring surface*, not a new language. This does mean Script content is locked into TypeScript for now — moving to a parsed DSL later (e.g. if non-programmer authoring becomes a real requirement) would mean rewriting existing Scripts, not just adding a parser alongside them.
