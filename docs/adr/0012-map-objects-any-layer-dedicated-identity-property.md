# Map objects can live on any object layer, and are identified by a dedicated property, not `name`

Supersedes two of ADR-0010's specific calls: that Spawn/Entity/Portal objects must live in one shared `objects` layer, and that an object's `name` field doubles as its id. Revisited while authoring Entities for ticket 05 hit two things ADR-0010 didn't anticipate: a Map with many tile-rendering layers still needs the freedom to place objects wherever makes sense without being boxed into one shared object layer, and `name` is a free-text display label Tiled never validates for uniqueness — while the codebase already had a different, unrelated precedent (the pre-existing `spawn_point` object's `spawn_key` property) using a dedicated property for identity instead.

We now allow Class-tagged objects on any number of object layers — the Class tag, not which layer an object sits on, is what tells Spawn/Entity/Portal apart, so the single-layer rule was never load-bearing. Identity now comes from a dedicated `entityId` Class-member property instead of `name`, so an object's display label can be edited for authoring clarity without silently changing the id a Script/Flag is keyed to. `entityId` was chosen over a `spawn_key`-style snake_case name because `spawn_key` turned out to be dead/temporary (the Engine reads spawn position from `WorldConfig`, never from the Tiled object) rather than a deliberate convention worth matching, and `entityId` is a direct, translation-free match to the existing camelCase field name already used on the TS side (`EntityObject.entityId`, `InteractedEvent.entityId`).

We considered going further and letting a Class-tagged Tile *Definition* alone (no placed object) produce an Entity, keyed by wherever it's painted. Rejected: a tile layer's cells carry no per-instance identity in Tiled's own data model, so an id would have to be synthesized from coordinates and would silently change if the tile moved — unacceptable given ticket 12's Script lookup keys directly off `entityId`.

Because identity no longer rides on a Tiled-enforced-unique field (nothing in Tiled enforces uniqueness on `name` or on a custom property), two objects can still collide on `entityId`. The Engine now warns (not errors) when two objects on the *same* Map share one. Uniqueness *across* Maps matters too — ticket 12's Script lookup has no per-Map scoping — but the Engine only ever loads one Map at a time (ADR-0001's stateless, single-Map contract), so that check belongs to a separate dev script over the whole Map catalog, not the Engine package.
