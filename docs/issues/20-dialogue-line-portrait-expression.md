# 20: Dialogue lines show a Portrait by Expression

**What to build:** A Dialogue line can select a Portrait via a fixed Expression value, bundled with its Speaker — the Host-side overlay renders the matching illustration, or falls back to text-only when none exists.

**Blocked by:** 18

**Status:** done

**Architecture note:** see `docs/spec/spec.md`'s "Dialogue Portraits & Expressions" section and `docs/adr/0014-dialogue-portraits-are-a-standalone-asset-type.md`.

**Implementation notes:** `script.ts` gains `export type Expression = 'Neutral' | 'Happy' | 'Sad' | 'Angry' | 'Surprised'` and `SayOptions.expression?: Expression`, passed through by `.say()` alongside `speaker` (present only when set, same as `speaker`) — spec's illustrative example bundled this as `portrait: 'happy'`, but the field is named `expression` here since its value is always one of the closed Expression set, and Portrait *resolution* (the actual asset lookup) is a separate concern from what a Script requests. `apps/web/src/state/portraits.ts`'s `resolvePortrait(speaker, expression, registry?)` is that resolution: a pure function, fixture-styled like `strings.ts`'s `resolveLine`, defaulting to a module-level `REGISTRY` object keyed by the exact Speaker string a Script uses (adr/0014) — declared via `satisfies PortraitRegistry` rather than a `.json` fixture or a `: PortraitRegistry` annotation, so a typo'd Expression key is a typecheck error rather than a silently-unwarned runtime miss. Unlike `player-assets.ts`'s `pickPlayerTexture`/`resolvePlayerTexture` split, there's no side effect to separate out (no placeholder texture to create, no `console.warn`) since a missing Portrait is an expected content gap, not a failure — one pure function covers it. Portrait art lives under the gitignored `assets/portraits/`, symlinked at `apps/web/public/assets/portraits` the same way `assets/sprites/` and `assets/maps/` already are; the new `docs/guides/dialogue-portrait-assets.md` covers the Expression-to-filename convention. `dialogue-overlay.tsx` resolves and renders the current line's Portrait as a plain `<img>` (an inline `oxlint-disable-next-line next/no-img-element`, since `next/image`'s `Image` can't take the `style` prop this repo's `react/forbid-component-props` rule requires going through a native element for) floated left at a fixed 64px display size. `entities/CampFire.ts`'s demo lines now carry Expressions end-to-end: the greeting cycles `Happy`/`Neutral` by `metBefore`, the nested memories round changes Expression line-to-line within the same round (`Sad` → `Neutral`, proving per-line not per-round resolution) across two different Speakers, and the trash-talk branch's `'Go away!'` line deliberately requests `Angry`, left unregistered, to exercise the text-only fallback. Demo registry entries (`Campfire`, `Narrator`) are committed pointing at the gitignored placeholder art — kept deliberately (user's call) to prove the mechanism end-to-end the way `CampFire.ts` already does for Speaker/locale, at the cost of a fresh clone seeing a blank image slot instead of text-only until real art is added.

- [x] Expression is a fixed, closed TypeScript union/enum (`Neutral | Happy | Sad | Angry | Surprised`); a Script can only request a value from this set — `Expression` in `script.ts`
- [x] A line's Portrait selection is bundled into the same per-line option as Speaker (not a separate builder step) — `SayOptions.expression`, alongside `SayOptions.speaker`
- [x] Portrait art lives in its own asset location, independent of the character-spritesheet pipeline — no dependency on the Speaker having an Entity, Player character, or spritesheet — `assets/portraits/`, keyed by raw Speaker string in `portraits.ts`'s `REGISTRY` (`Narrator` has no Entity)
- [x] A pure function resolves (Speaker, Expression) to a Portrait asset reference or `undefined`; `undefined` renders as text-only with no warning — `resolvePortrait` in `portraits.ts`
- [x] The Host-side overlay renders the resolved Portrait image alongside its line when one exists — `dialogue-overlay.tsx`
- [x] The `ScriptBuilder`'s portrait/Expression output and the Portrait-resolution function are both unit-tested (`node:test`) — `scripts.test.ts`, `portraits.test.ts`
